Bagaimana adm-masjid dan web-masjid sebenarnya terhubung

Kedua aplikasi kini satu project Vercel (root = masjid/, mis. kasolmasjid.vercel.app) yang hanya bertemu di satu tempat lain: tabel masjid_website di Supabase. Admin di /adm/ menulis lewat RPC sesi akun, website publik di /<slug> membaca lewat REST publik dengan anon key — dan saat slug punya domain TLD aktif, /<slug> otomatis redirect ke TLD itu.

Peta besar: satu sumber data, dua etalase

Semua yang tampil di website publik berasal dari satu baris per slug di tabel masjid_website — kolom data (live) dan draft (pratinjau).

Gambar 1 — Admin dan web tidak saling memanggil; keduanya hanya membaca/menulis tabel yang sama di Supabase.

Alur "Publikasikan": dari klik admin sampai tampil di web

Satu klik di admin = satu RPC masjid_publish_by_account = satu baris masjid_website yang di-upsert. Web publik langsung membaca hasilnya tanpa proses build.

  1. Admin klik "Publikasikan"

    Payload dibangun lokal: buildWebsiteDraftPayload() = data utama + editorial (hero, sambutan, pengumuman, galeri). adm-masjid/index.html:2592

  2. RPC dipanggil dengan sesi akun

    publishViaAkun() → rpc('masjid_publish_by_account', { p_slug, p_data }). Slug diambil dari situs aktif server (slugAktif()), bukan diketik manual. index.html:3281–3307

  3. Server memeriksa identitas & peran

    current_global_identity_id() dari JWT → cari slug di masjid_sites → masjid_site_role harus owner, selain itu hasil forbidden. Token publish lama tetap di-upsert untuk kompatibilitas. migration-masjid-hub-site.sql:388–452

  4. Upsert ke tabel publik

    insert into masjid_website (slug, data, published_at, updated_at) … on conflict (slug) do update. Satu baris per slug — publish berikutnya menimpa yang lama. migration-masjid-hub-site.sql:435–440

  5. Web publik membaca saat halaman dibuka

    loadData(slug) → GET /rest/v1/masjid_website?slug=eq.<slug>&select=data,draft,published_at dengan header apikey (anon). RLS mengizinkan select publik; bila gagal/ kosong, fallback ke file /data-website.json. web-masjid/index.html:558–575

Draft & preview: kolom terpisah, live tidak terganggu

Menyimpan draft memanggil RPC berbeda yang hanya menulis kolom draft — kolom data (live) tidak disentuh. Preview membuka web dengan parameter khusus.

Simpan draft
draftViaAkun() → masjid_draft_by_account(p_slug, p_data) → on conflict do update set draft = excluded.draft saja. index.html:3308–3314 · hub-site.sql:457–499
Buka preview
window.open(webBaseUrl() + '?preview=1&slug=' + slug) — model 1-project: di produksi webBaseUrl() = location.origin + '/' (admin & web satu origin), saat lokal otomatis /web-masjid/. adm-masjid/index.html:2275–2286, 2619
Host web
Tidak ada lagi konstanta WEB_BASE_URL; URL publik yang ditampilkan admin = <origin>/<slug> (tanpa m/). adm-masjid/index.html:3322
Mode preview di web
PREVIEW = ?preview=1; bila aktif dan ada draft, web memakai draft.editorial + menampilkan banner "Mode Preview". Tanpa parameter itu, yang tampil selalu data live. web-masjid/index.html:516, 784–792

Satu web-masjid melayani banyak masjid: resolusi slug

Web-masjid itu multi-klien: satu deploy untuk semua masjid, slug menentukan masjid mana yang ditampilkan. Urutan penentuannya (prioritas dari atas):

1
?slug=<slug> di URL Override manual / dipakai link preview dari admin. web-masjid/index.html:517,551
2
Path /<slug> (atau /m/<slug> lama) Model 1-project: slug langsung di belakang origin (kecuali path cadangan adm, assets, dst.). index.html:523–535 (slugDariPath)
3
Host custom domain → RPC masjid_resolve_domain(host) Host TLD klien (mis. masjidkita.my.id) dipetakan ke slug lewat tabel masjid_website_domains yang statusnya active. Host platform (vercel.app) dilewati — di host platform slug diambil dari path. index.html:536–575 · hardening F1
4
Redirect /<slug> → TLD aktif Di host platform, bila slug punya domain active, web memanggil RPC masjid_domain_for_slug(slug) lalu location.replace('https://<tld>/…'). index.html:~815 · migration-masjid-one-project.sql
5
Default 'masjid' Bila semua di atas gagal/offline. index.html:470

Siklus domain custom (Claim Domain) — sudah di-hardening F1–F3

Domain klien diklaim lewat admin, diverifikasi lewat DNS, lalu dipakai masjid_resolve_domain saat pengunjung membuka domain tersebut.

  1. Klaim

    masjid_claim_domain(domain, site_id) → status pending + token verifikasi. Host platform (*.vercel.app, vercel-dns.com, daftar tabel masjid_reserved_domains) ditolak (domain_reserved) — F1. Domain yang sudah active tidak diturunkan diam-diam; hasilnya domain_already_active dan admin ditawari re-klaim eksplisit lewat masjid_reclaim_domain — F2.

  2. Set DNS di registrar klien

    Admin menampilkan box instruksi (CNAME ke host Vercel + TXT berisi token), tombol "Cek Verifikasi". adm-masjid/index.html:3339–3435 (renderDnsBox)

  3. Verifikasi

    masjid_verify_domain(domain, token) → bila cocok, status naik active. Token lama yang sudah dipakai menjadi invalid_token.

  4. Pakai

    Pengunjung membuka domain → web-masjid memanggil masjid_resolve_domain → dapat slug → loadData(slug) → halaman masjid yang bersangkutan tampil. Domain terlarang selalu not_found walau (secara tak mungkin) ada baris aktif — F1.

Intisari satu paragraf

adm-masjid dan web-masjid tidak saling memanggil secara langsung — keduanya hanya berbagi satu tabel di Supabase, meski kini di-serve dari satu project Vercel (root masjid/): admin di /adm/, website klien di /<slug>. Admin menulis lewat RPC sesi akun (masjid_publish_by_account untuk live, masjid_draft_by_account untuk draft) yang menulis baris masjid_website per slug setelah memeriksa bahwa pemanggil adalah owner situs itu. Website publik membaca baris yang sama via REST publik saat halaman dibuka, memilih slug dari ?slug= → /<slug> → domain custom via masjid_resolve_domain → default masjid, lalu merender data (atau draft saat mode preview). Bila dibuka di host platform dan slug punya domain TLD active, halaman otomatis redirect ke TLD via RPC masjid_domain_for_slug. Domain custom klien diklaim dan diverifikasi lewat DNS di admin + di-attach ke project Vercel (DNS saja tidak cukup), dan sejak hardening F1–F3 host platform tidak bisa diklaim dan domain aktif tidak bisa "mati" tanpa konfirmasi eksplisit.
